The [report-data binding](/privacy/tee-attestation/freshness-binding) commits a report to the signing address plus your nonce. This page covers two precise invariants about how that address-based binding is validated in the nested model attestation (gate 6 of the [seven-gate baseline](/privacy/tee-attestation/seven-gate-baseline)). They are narrow, but getting them right is the difference between a binding that means something and one that does not.

## What "Binding" Means

A binding is the link that says "this attestation belongs to this specific thing." An attestation that is signed correctly but not bound to anything is like a notarized signature on a blank page: genuine, but it proves nothing about a particular document. Binding is what staples the proof to a concrete identity, so an attacker cannot take a valid-looking proof and pass it off as covering something it never covered.

This page is about two ways that staple could be weaker than it looks, and the rules that keep it strong. You do not run these checks yourself (Nito's baseline runs them), but understanding them tells you exactly what a baseline-verified result does and does not prove, which is the kind of thing a security reviewer will want to pin down.

## Binding Uses the Signing Address Only

The binding is keyed on the **signing address**, not on the model public key. The address is the identity the report commits to. This is a deliberate choice: the address is the stable, comparable handle that is recomputed and matched against the report data.

But there is a trap in keying on the address alone, and the second invariant closes it.

### An Entry Without a Model Public Key Is NOT a Binding

When the model attestation is walked looking for a binding, an **evidence entry that lacks a model public key does not count as a binding.** An address match alone is not accepted: the model public key must be present for the entry to qualify.

This means the model public key is **always validated** as part of accepting a binding. You never reach a state where an address binding is confirmed while the model public key is missing. If the public key is absent from an entry, that entry simply is not a binding, and the search continues or the gate fails.

### Why This Invariant Matters

Without it, the address-only binding would be weaker than it looks. An attacker who could present an evidence entry that matched the expected signing address but carried no model public key could try to pass it off as a valid binding without ever committing to a model identity. By refusing to count keyless entries as bindings, every accepted binding is guaranteed to tie together both the signing address _and_ a concrete model public key. The two travel together or not at all. (Recall from the [pipeline page](/privacy/tee-attestation/attestation-pipeline) that the signing key and the model public key are two names for this same key value, so there is exactly one key value in play here.)

## The Top-Level and Model Signing Addresses Are Kept Separate

There are two signing addresses in play: the top-level one and the model's. Nito keeps them **separate**, and the baseline does **not** require them to be equal. A reader might assume that a valid attestation means the top-level report and the model share one signing identity. That is not the invariant. The baseline checks each binding on its own terms; it does not collapse the two addresses into one or demand that they coincide.

### Why This Separation Matters

Keeping the addresses distinct means the top-level report-data binding and the nested model-attestation binding are evaluated independently. A correct result does not depend on, and does not assert, that the top-level report and the model are the same signer. If you are reasoning about what a baseline-verified result proves, do not over-read it: it confirms that each binding held against its own address, not that there is a single shared signing identity behind both.
