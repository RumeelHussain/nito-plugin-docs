---
title: "Per-Provider Attestation"
description: "Why attestation evidence can look different depending on which sealed-compute backend served your call, and why the guarantee you get is the same across all of them."
---

Nito can route your private call to more than one sealed-compute backend. Each backend runs its own hardware and its own way of vouching for the workload it sealed, so the attestation evidence they produce is not byte-for-byte identical. This page explains where those differences show up, and why they do not change the guarantee you get: a signed proof you can verify independently.

## The Attestation Subject

When a sealed environment produces an attestation, the signed statement has to say _what_ it is vouching for. The **attestation subject** is that identity anchor: the name the proof is bound to, so you can confirm the evidence belongs to the workload you meant to run and not some other environment. Think of it as the name on a notarized document. The notary's stamp (the hardware signature) proves the document is genuine; the name on it tells you whose document it is. Different backends stamp the document the same way, but they may write the name in different fields.

Why more than one backend at all? Each runs its own sealed-compute infrastructure, so each has its own way of naming the workload it sealed. Nito normalizes everything else, but it cannot erase this structural difference, so it surfaces it to you in the result. Knowing that the naming can differ means you can read an attestation from any backend without surprise.

## What Backends Share

Whichever backend served your call, the evidence flows through the same [attestation pipeline](/privacy/tee-attestation/attestation-pipeline) and is parsed the same way. From Nito's perspective, every backend feeds into the same [seven-gate baseline](/privacy/tee-attestation/seven-gate-baseline) and the same result shape. The differences are confined to how the subject is named and whether a subject is required.

## Where Backends Can Differ

The structural differences between backends come down to a few fields:

| Aspect | Varies by backend |
| --- | --- |
| How the subject is named | The field used to name the attested workload can differ from one backend to another |
| Whether a subject is required | Some backends always carry a subject; others treat it as optional |
| Default proof format | Each backend labels its evidence with its own proof-format identifier |

None of this changes what the proof _means_. It only changes how you read the fields when you inspect the evidence.

## How This Surfaces in the Result

In the [attestation result](/privacy/tee-attestation/attestation-pipeline), a proof-format label tells you which backend produced the evidence, and a subject field (when present) carries the name the proof was bound to. The exact identifiers vary by backend, so read the fields on the result you actually received rather than assuming a fixed shape.

This per-backend distinction does not change the verification contract you run. Whichever backend served the call, the [seven-gate baseline](/privacy/tee-attestation/seven-gate-baseline) and the [verify-yourself path](/privacy/tee-attestation/verify-yourself-recipe) apply the same way. The subject naming is something to be aware of when you read the result, not a separate verification flow.

Which backend serves a given model is discovered at runtime and reported per model, so read it from the model's own attestation metadata rather than a static list. Each model is served by exactly one backend, so there is never ambiguity about which evidence format applies.
